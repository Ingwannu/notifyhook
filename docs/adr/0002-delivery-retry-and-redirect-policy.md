# ADR 0002: 전송 재시도 분류, 재시도 기간, 리다이렉트 미추적

- 상태: 채택 (1.0.36)
- 관련 코드: `service/DeliveryRetryPolicy.kt`, `service/HookDeliverySender.kt`, `service/NotificationListener.kt`, `service/HookDeliveryWorker.kt`

## 배경

1.0.35까지의 동작:
- 모든 실패(4xx 포함)를 10초부터 최대 15분 간격으로 **기한 없이** 재시도했다. 잘못된 API 키(401)나 경로(404)도 영원히 재전송되었고,
  재시도 큐가 남아 있는 동안 포그라운드 서비스도 계속 유지되었다.
- OkHttp 기본값대로 리다이렉트를 따라갔다. OkHttp는 301/302/303에서 POST를 **본문 없는 GET**으로 바꿔 보낸다.
  예를 들어 `http://` → `https://` 301 리다이렉트가 있으면 서버는 알림 내용을 받지 못했는데 로그에는 "성공(200)"이 남았다
  (MockWebServer로 기존 코드에서 재현함).
- 다른 호스트로 리다이렉트되면 OkHttp는 `Authorization`만 지우고 `X-API-Key` 같은 사용자 헤더는 그대로 보낸다. 헤더 기능(ADR 0001)을 넣으면 키가 제3자에게 넘어갈 수 있다.

## 검토한 대안

재시도
1. 기존처럼 모든 실패 재시도: 일시 장애에 강하지만 설정 오류도 영구 재시도된다.
2. 최대 시도 횟수만 제한: 백오프 간격이 바뀌면 실제 보장 기간이 달라져 설명하기 어렵다.
3. 상태 코드 분류 + 생성 시점 기준 기간 제한: 일시 장애만 재시도하고 기간이 명확하다.

리다이렉트
1. 기존처럼 따라가기: 위의 본문 유실·키 유출 문제가 남는다.
2. 같은 호스트의 307/308만 따라가기: 직접 인터셉터를 구현해야 하고, 규칙이 복잡해 사용자가 예측하기 어렵다.
3. 따라가지 않고 실패로 기록하며 Location을 안내: 사용자가 최종 URL로 한 번 고치면 끝난다.

## 결정

- 재시도 대상: 네트워크 오류(응답 없음), 408, 425, 429, 5xx.
- 재시도하지 않음: 그 외 4xx, 3xx, 요청을 만들 수 없는 형식 오류(잘못된 URL/메서드/헤더). 큐에서 지우고 로그에 `(not retried: request must be fixed)`를 남긴다.
- 재시도 기간: 요청 생성 후 24시간. 넘으면 `(not retried: 24h retry window exceeded)`로 기록하고 버린다.
  휴대폰 재부팅이나 서버 점검처럼 하루 안의 장애는 버티고, 오래된 알림이 며칠 뒤 한꺼번에 도착하지 않는 선이다.
- OkHttp 클라이언트는 `followRedirects(false)`, `followSslRedirects(false)`. 3xx는 `HTTP 301 redirect to <Location>; ...` 오류로 기록한다.
- 백오프 간격(10초 × 2^n, 최대 15분)은 그대로 둔다.

## 결과

- 설정 오류는 한 번 실패 로그로 끝나 사용자가 바로 알아챌 수 있다. 서버에도 불필요한 반복 요청이 가지 않는다.
- 리다이렉트를 쓰던 서버는 1.0.36부터 실패로 표시된다. 로그와 테스트 결과에 표시되는 Location으로 URL을 바꿔야 한다.
- 24시간 넘게 꺼져 있던 기기의 대기 요청은 전송되지 않는다.
